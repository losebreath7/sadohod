# Git workflow — Садоход

## Основные ветки
- `main`: только подтверждённая рабочая версия; обновлять после успешных проверок.
- `develop`: текущая интеграционная версия.
- `fix/*`, `feature/*`: отдельные изменения с Pull Request в `develop`.

## Перед переносом исходников
1. Исходник: последний проверенный локальный проект R8 0.8.4+27 **WITH_GATE**.
2. Переносить исходные файлы в клонированную папку репозитория, сохраняя `server/`, `buyer_app/`, `seller_app/`, `shared/`, `tools/`.
3. Не переносить рабочие `.env`, базы данных, тома PostgreSQL, пользовательские фотографии, резервные копии и `gate-logs/`.
4. Перед первым коммитом изучить список *Changes* в GitHub Desktop: проверить отсутствие секретов, личных данных и временных файлов. Если есть сомнения — остановиться.

## Проверка
- Локально: `ВОРОТА.bat` (не пропускать этапы).
- Для успешной проверки необходим код завершения **0**.
- `gate-logs/` не хранится в Git.
- Сборки Flutter Web и фактическое поведение обоих приложений в Chrome проверяются отдельно от серверных тестов.
- Если тесты недоступны или пропущены, не представлять версию как проверенную.

## Данные
Docker Volumes и рабочая PostgreSQL остаются на компьютере владельца. Git не переносит и не обновляет их. Изменения схемы данных — отдельными проверенными миграциями, с резервным копированием перед применением.

## Параллельная работа нескольких чатов (16 ноября 2026)

### Назначение веток
- `develop` — единая интеграционная ветка. Не отправлять в неё рабочие коммиты напрямую: использовать Pull Request.
- `main` — только стабильные релизы после подтверждения владельцем; предпочтительно PR из `develop`. Не отправлять напрямую.
- `feature/buyer` — работа отдельного чата над покупателем (`buyer_app/`).
- `feature/seller` — работа отдельного чата над продавцом (`seller_app/`).
- `feature/moderation-workspace` — изолированная работа над кабинетом модерации.
- `fix/buyer-home-logo-tags` — отдельное исправление главной покупателя; держать PR черновиком до проверки в браузере.
- Для новых независимых задач использовать `fix/<задача>`, `feature/<задача>` или `docs/<задача>` от актуальной `develop`. Не коммитить в чужую ветку без согласования.

### Перед каждой задачей
1. Проверить HEAD `develop`, активную рабочую ветку, открытые Pull Request и пересечения по файлам с другими чатами.
2. Открыть утверждённый макет Figma нужного экрана; не изобретать новые экраны, если утверждённый макет уже существует.
3. Определить конкретные файлы/сценарии. При пересечении с другой веткой согласовать порядок изменений до записи.
4. Не переносить изменения из одной ветки принудительным `push --force` или перезаписью чужих коммитов. Не сливать ветки вслепую.
5. Изменять код только после команды владельца «старт» для соответствующей задачи.

### Готовность Pull Request в develop
- Создать PR из рабочей ветки в `develop`; до проверки держать в статусе Draft.
- Дождаться успешного GitHub Actions `gate`: версии, изолированный сервер (SQLite/PostgreSQL), оба Flutter-приложения (`analyze`, `test`, `build web`). Проверять результат для **последнего** commit SHA, а не прежнего запуска.
- Для UI отдельно проверить в реальном Chrome обе важные ширины (включая предпросмотр iPhone 16 Pro), интерактивность, скролл, переходы и соответствие Figma. CI не заменяет проверку UI. Указать явно, если браузерная проверка не проводилась.
- Для серверных изменений проверить оба клиента и существующий API; миграции выполнять отдельно с резервной копией на тестовой БД.
- В PR указать перечень изменённых файлов, ограничения проверки, результат CI, визуальную проверку и потенциальные конфликты.
- Объединять только после подтверждения владельцем. Если это только документация, отдельно указать, что UI-проверка неприменима.

### Обновление main
1. Убедиться, что `develop` прошла тесты, ручную визуальную проверку и согласована владельцем.
2. Открыть PR `develop → main`; не делать прямого push.
3. После релиза обновить локальный клон GitHub Desktop и перезапустить нужное приложение. Изменения на GitHub **не** обновляют уже запущенный Flutter в Chrome автоматически.
4. Не удалять Docker Volumes, данные PostgreSQL, фото, локальные `.env` или старую рабочую сборку при переносе изменений.

### Ограничение защиты
По состоянию на 16.11.2026 обе ветки `main` и `develop` отмечены GitHub как `protected: false`. Для правил защиты приватного репозитория GitHub возвращает ограничение тарифа (предлагает GitHub Pro). Пока защита не включена на стороне GitHub, этот документ — **договорённость, а не технический запрет** прямого push. Не выдавать её за включённую branch protection.
