# R23 — фотопоиск перед публичным запуском

## Изменения поисковой выдачи
- Фотографии товаров без действующего предложения (`offers`) больше не
  допускаются в векторную выдачу в PostgreSQL и SQLite. Это также исключает
  изображения сохранённых черновиков продавцов, которые уже проиндексированы.
- OpenCLIP без явного порога больше не возвращает все подряд «ближайшие»
  элементы. Начальный нижний порог косинусного сходства —
  `PHOTO_SEARCH_MIN_SCORE=0.20`. Запрос может поднять, но не опустить
  этот порог. Результат — **не вероятность** совпадения.
- Для устранения монополизации топа товарами с несколькими фотографиями
  увеличено число кандидатов перед дедупликацией по product_id до
  `max(128, min(600, 12 * limit))`. Перед production нужно проверить влияние
  на p95 latency.
- Classic-режим оставлен для локальной совместимости, но он не является
  семантическим поиском и не годится для публичного обещания «по фото».

## Проверки
Тесты: HTTP отказ в слабых совпадениях, заданный пользователем строгий порог,
сильное совпадение, исключение фотографий без offer, расчёт показателей
контрольной выборки. Это **контрактные тесты**, не проверка реальной точности
модели OpenCLIP.

Для реальной приёмки собрать независимые фотографии вещей, которых **нет**
в исходных картинках каталога (другой ракурс, фон, свет); для каждого запроса
записать допустимые ID похожих продуктов. Добавить фотографии, для которых в
каталоге заведомо нет аналога.

Пример JSON, хранить **вне репозитория**:

```json
[
  {"image": "bag-other-angle.jpg", "expected_ids": ["real-product-id"]},
  {"image": "irrelevant.jpg", "expect_empty": true}
]
```

Из каталога `server/` с доступным сервером:
```bash
python -m backend.tools.evaluate_photo_search_live \
  --manifest /private/photo-queries.json \
  --api https://api.example.com \
  --min-hit5 0.8 --max-p95 3.0 \
  --output /private/photo-benchmark.json
```

Скрипт отправляет запросы в настоящий HTTP API и прекращает проверку, если
сервер отвечает не режимом `openclip_image_embedding`. Вычисляет hit@5,
долю корректно пустых запросов, p50/p95 задержки. Если выбранные целевые
значения не достигнуты, завершает работу с кодом ошибки. Эти цели не должны
выдаваться за уже измеренные результаты. Порог 0.20 — отправная точка,
перебрать несколько значений на независимой выборке для каждой категории.

## Перед staging
1. Запускать `docker-compose.ml.yml` поверх базового Compose, проверить
   `GET /health`: `search_backend=clip`.
2. Проверить количество фотографий с текущими ML embedding и pgvector mirror;
   не публиковать пустой или устаревший индекс.
3. Разделить тяжёлую индексацию и готовность публичного API; сейчас
   `index_catalog` пересматривает все фотографии при старте.
4. Отключить `DEMO_SEED`, выставить секреты через приватный .env,
   ограничить доступ к PostgreSQL и админке, обеспечить HTTPS и защиту
   загрузок от исчерпания ресурсов.
5. Настроить резервные копии базы **и** `sadohod_uploads` с проверкой
   восстановления на отдельном окружении. Не удалять существующие volumes.
6. Сначала staging на новом VPS; не подключать оба приложения к нему как к
   production до пройденной приемки поиска и повторного тестирования
   регистрации, модерации, публикации, чатов и фотографий.

**Этот PR не переносит данные и не меняет запущенное окружение.**
