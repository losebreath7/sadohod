# Садоход — независимость от VPS и переезд без обновления приложений

Статус: инженерная инструкция. Не является отчётом об успешной миграции.
Область: **два Flutter-клиента + общий FastAPI/PostgreSQL/OpenCLIP**.
Домен `sadohod.ru` и DNS управляются в REG.RU **отдельно от VPS**.
Никакие команды этого файла не изменяют DNS или рабочие контейнеры автоматически.

## Постоянные адреса

| Адрес | Назначение |
| --- | --- |
| `sadohod.ru` / `www.sadohod.ru` | Текущий сайт, его DNS не менять при миграции API |
| `api.sadohod.ru` | **Единственный production origin** API обоих приложений |
| `api-stage.sadohod.ru` | Временный DNS для проверки нового VPS; не встраивать в App Store/Play |

Flutter-клиенты используют `API_BASE_URL`, общий обработчик —
`shared/flutter_core/lib/api_base_url.dart`. Мобильный release отвергает HTTP,
localhost, прямые IPv4/IPv6, URL с учётными данными, портом, путём, query
или fragment. Относительные URL фотографий `/media/products/...`
прикрепляются к текущему `baseUrl`.

Собирать публикуемые бинарные приложения через
`python tools/build_store_release.py --app buyer_app --platform android`
(или `seller_app`, `ios`). Скрипт задаёт неизменный
`https://api.sadohod.ru`. Подписание, TestFlight/Google Play, реальные устройства
и ручная проверка обязательны, скрипт их не заменяет.

**Не встраивать IP, URL тарифного кабинета, временный staging host или
URL с портом 8000 в опубликованные приложения.** При обычной смене VPS
публикация новой версии не нужна; при смене самого `api.sadohod.ru` уже
может понадобиться обновление клиента.

## Первое развёртывание на AdminVPS (или любом другом VPS)

1. В REG.RU создать A-запись **только** `api.sadohod.ru` на основной IPv4 VPS.
   Убедиться, что старых/лишних AAAA-записей нет (если IPv6 не настроен).
   Не менять записи основного сайта. Управлять сроком жизни DNS (TTL).
2. На VPS: Ubuntu, доступ по SSH-ключам, firewall, Docker Engine + Compose,
   наблюдение за диском, RAM, CPU; наружу только HTTPS 443, HTTP 80 и
   ограниченный административный SSH. Не открывать PostgreSQL 5432 и API 8000.
3. Развернуть из проверенного SHA `docker-compose.production.yml` в
   **отдельном** проекте `sadohod_public`, а не в локальном `sadohod_mvp_v0_2`.
   Установить `API_DOMAIN=api.sadohod.ru` в `.env.production`.
   Подготовить SMTP, случайные `POSTGRES_PASSWORD` и `ADMIN_TOKEN` за пределами Git.
4. Выполнить `python3 tools/check_production_env.py --env .env.production`,
   `docker compose --env-file .env.production -f docker-compose.production.yml
   -p sadohod_public config --quiet`, затем штатный запуск по
   `docs/PRODUCTION_DEPLOYMENT.md`.
5. Проверить сертификат Caddy, `https://api.sadohod.ru/health` (demo=false,
   search_backend=clip), выдачу OTP, создание и просмотр товара, фото, поиск,
   чат, модерацию, уведомления на **двух** физических клиентах.
6. Протестировать внешний backup и восстановление. Рабочую БД на новом публичном
   сервере не наполнять демонстрационными данными.

## Подготовка к переезду на другого провайдера

- Домен остаётся в REG.RU. За 24–48 часов снизить TTL A-записи `api.sadohod.ru`
  до примерно 300 секунд. Фактическое кэширование DNS может быть дольше TTL.
- Зафиксировать SHA релизного коммита, Alembic revision, версии PostgreSQL,
  настроек OpenCLIP, CORS, SMTP и доверенных прокси. Провайдерский IP не должен
  встречаться в исходящих URL API, картинках, callback URL и клиентах.
- Поднять **изолированный** новый VPS с нужными CPU/RAM/диском. Старый
  сервер пока остаётся единственным принимающим записи.
- Для предварительного TLS-теста можно создать `api-stage.sadohod.ru` с A-записью
  на **новый** IP, развернуть там временный `API_DOMAIN=api-stage.sadohod.ru`
  и выпустить действительный сертификат Caddy для staging. Никаких реальных
  пользовательских записей в отдельной staging-БД.
- Проверить TLS и здоровье напрямую, без изменения production DNS:
  `SADOHOD_API_HOST=api-stage.sadohod.ru bash tools/check_api_candidate.sh NEW_IPV4`.
  Скрипт выполняет только GET `/health`, проверяет HTTPS-сертификат и
  `demo=false, search_backend=clip`. Он не тестирует OTP или реальные записи.
- **Внимание к TLS.** Публичный сертификат для `api.sadohod.ru` на новом
  VPS нельзя гарантированно получить через обычный HTTP-01/TLS-ALPN-01
  до переключения DNS: проверка домена придёт на старый сервер.
  Поэтому заранее подготовить согласованную схему выдачи сертификата
  (DNS-01 или безопасный перенос действительного Caddy TLS-state); либо
  предусмотреть короткое окно обслуживания после переключения.
  Никогда не использовать `curl -k` как критерий готовности.
- Перед переездом убедиться, что на новом сервере есть достаточно места для
  **базы, фотографий, служебных данных, временного архива и запаса**.

## Что именно переносить

| Что | Откуда | Проверка |
| --- | --- | --- |
| База и сессии покупателей/продавцов | `public_pg` / согласованный `pg_dump` | `pg_restore`, количество записей, сохранение авторизации |
| Загруженные фотографии | `public_uploads` | SHA256 и доступность фото по API |
| Административное состояние | `public_admin_state` | Проверить восстановление соответствующих функций |
| Опубликованные правовые документы | `./legal_published` | **Не входят** в штатный backup-архив, копировать отдельно |
| Секреты SMTP/PostgreSQL/ADMIN_TOKEN | защищённое хранилище оператора | Сверить, не раскрывать через Git или чат |
| ML-кэши и веса | `public_ml_cache` | Можно повторно загрузить/пересоздать, проверить поиск и время старта |
| TLS-материалы | `public_caddy_data` или новая выдача | Действительный сертификат и автопродление |

Штатный `tools/backup_production.sh` создаёт `database.dump`,
`user-volumes.tar.gz` (uploads/state) и контрольные SHA256. Он **не**
создаёт атомарный общий snapshot БД и файлов. Для окончательной копии
нужно отключить загрузки и остальные операции записи на старом API.
`tools/restore_drill.sh` восстанавливает данные только в **новые
изолированные QA-volumes**, не в production. Восстановление реальной БД
на новом VPS проводить отдельно по `docs/PRODUCTION_DEPLOYMENT.md`,
без перезаписи старых данных.

Сессии покупателей в коде представлены хэшами токенов в PostgreSQL.
Без переноса базы и её записей активные пользователи могут потерять вход.
Поэтому нельзя разворачивать пустую базу при миграции реальных аккаунтов.

## Окончательное переключение DNS (maintenance window)

1. Объявить короткое окно обслуживания. Остановить **все операции записи**
   на старом API, включая загрузку товаров, сообщения и фоновые задачи.
   Обычный DNS-switch без этого создаёт две расходящиеся базы данных.
2. Создать финальный согласованный backup БД + uploaded media + state;
   проверить SHA256 и сохранить копию **вне обоих VPS**.
3. Восстановить на новом VPS и проверить целостность связей БД с фото,
   наличие аккаунтов и сессий. Сохранить совместимость API и схему БД.
4. Настроить на новом VPS `API_DOMAIN=api.sadohod.ru`, обеспечить
   **действительный TLS-сертификат** (см. ограничение ACME выше), прогнать
   `bash tools/check_api_candidate.sh NEW_IPV4` по каноническому домену
   после готовности сертификата и проверить критичные сценарии вручную.
5. Изменить **только** A-запись `api.sadohod.ru` в REG.RU на новый IPv4.
   Не менять `sadohod.ru`, `www`, MX или существующий сайт.
6. Убедиться, что запросы пользователей больше не выполняют записи в старую БД.
   При необходимости заранее подготовить проверенное проксирование
   старого HTTPS-трафика на **новый** API на период DNS-кэширования,
   но **не запускать старый API с собственной доступной для записи БД**.
7. Проверить оба приложения с мобильного интернета и Wi-Fi: OTP, сессии,
   избранное, товары, фотографии, поиск OpenCLIP, чаты и модерацию.
   Проверить сообщения об ошибках, сетевую задержку и журналы.
8. Держать старый VPS и проверенные бэкапы до окончания контрольного периода.
   Не удалять volumes, пока не подтверждена целостность, и только потом
   отключать старый хостинг.

**Откат:** если новый сервер уже принял записи, просто вернуть DNS на
старую БД **нельзя** — новые данные потеряются. При аварии остановить
записи, сохранить состояние нового сервера, затем восстановить/реплицировать
в единый источник истины и только после этого менять DNS обратно.

## Ограничения и приёмка

- Нет подтверждённого «нулевого простоя»: без репликации и управляемого
  переключения БД предусматривается короткое окно обслуживания.
- Не проверено до покупки VPS: реальный DNS REG.RU, работа сертификата,
  SMTP на провайдере, производительность OpenCLIP, восстановление
  production-данных и поведение физических устройств при смене IP.
- Обязательны `python3 tools/test_api_portability.py`, тесты Flutter, CI,
  тестовый перенос на отдельные volumes, мониторинг ошибок и проверка
  TLS. Отчёт CI сам по себе **не равен** успешной проверке переезда.
- В случае платного ухода от провайдера отдельно проверить условия
  биллинга/сроки отключения, стоимость исходящего трафика и хранение
  резервных копий согласно действующему договору.
