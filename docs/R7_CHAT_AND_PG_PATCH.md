# R7 (build 25): чаты, центрирование полей и PostgreSQL

## Изменения

1. `server/backend/app/merchant.py`: в трех блокировках `Seller` для создания дополнительного павильона, повторной отправки отклонённой заявки и решения администратора задано `with_for_update(of=Seller)`. Это исключает `FOR UPDATE` на nullable-таблице `pavilions` при joined eager loading.
2. `server/backend/app/merchant_chat.py`: добавлен `POST /api/v1/merchant/chat/messages/attachment`, использующий аутентификацию продавца, отдельные пространства `m_support`/`m_cooperation`, серверную валидацию JPG/PNG/WebP/PDF/TXT, лимит 3 МБ, сохранение в существующие таблицы и Telegram-outbox. Без миграции и без отдельного хранилища.
3. `shared/flutter_core/lib/chat_widgets.dart`: общая Figma-совместимая разметка сообщений и панели отправки для обеих Flutter-программ (аватар, время, две галочки, вложения, поле сообщения и кнопки). Покупатель использует тот же ранее утверждённый визуальный алгоритм, но общие компоненты больше не дублируются.
4. `seller_app/lib/seller_telegram_chat.dart`: показывает сообщения в порядке newest-bottom, поддерживает реальную отправку вложений, отображение превью и автоответов, переносит внешний вид из приложения покупателя; паттерны поддержки и сотрудничества взяты из сохранённых Figma-ассетов. Отдельные маршруты продавца не изменены. Нижняя навигация продавца сохранена; на экранах чата подсвечена вкладка профиля.
5. `seller_app/lib/seller_v3.dart`: в `V3Field` введённый текст теперь по вертикали центрируется в белом поле независимо от верхней подписи. Горизонтальное выравнивание не менялось.

## Проверка

- Адресные серверные тесты: `37 passed`, включая маршруты товаров/магазинов, обработку заявок, Telegram, приватность вложений и PostgreSQL SQL-компиляцию.
- Дополнительные серверные тесты на чаты и заявку: `24 passed` (частично перекрывают набор выше).
- Новые тесты на регрессию `FOR UPDATE` и seller attachment: `4 passed` вместе.
- Код Python скомпилирован `compileall`; строгая версия сборки и контроль состава ZIP выполняются в `tools/package_release.py`.
- Полный серверный набор в этой среде не завершился в лимит одного запуска: он **не считается пройденным**.
- Локальный PostgreSQL здесь не поднят. Компиляция SQL под PostgreSQL подтверждает `FOR UPDATE OF sellers`, но **не** заменяет реальный PG-прогон.
- Flutter SDK, Docker Engine и доступ к Windows-установке отсутствуют: `flutter analyze/test`, визуальный тест в Chrome и интеграционный запуск на пользовательской базе здесь **не выполнялись**.

## Как проверить у себя

1. Сохрани предыдущую рабочую папку R7. В новую папку распакуй ZIP и запусти «ОБНОВИТЬ САДОХОД.bat». Не запускай «ПЕРВЫЙ ЗАПУСК» при существующей базе; не удаляй Docker Volumes.
2. Запусти «ПРОВЕРИТЬ СЕРВЕРНЫЕ ТЕСТЫ.bat»: должен отработать SQLite и изолированные PostgreSQL тесты, включая четыре ранее указанных. Скрипт использует отдельную тестовую БД.
3. Продавец: открыть профиль → «поддержка» и «сотрудничество»; проверить отправку текста, фото, PDF и TXT, одноразовый автоответ, сообщение Telegram-менеджера, скролл, клавиатуру и возврат назад. Для обоих чатов проверь паттерны на фоне.
4. Покупатель: открыть такие же чаты, убедиться, что они не смешиваются с продавцом, а прежний интерфейс и отправка файлов работают как раньше.
5. Проверить редактирование полей «имя», «телефон», «павильон», «название», «цена» на ширине 390/402 px: значение должно быть по центру по вертикали, подпись сверху, текст слева.
6. На PostgreSQL пройти три проблемных API: добавление павильона, повторная отправка отклонённого дополнительного павильона и одобрение/отклонение администратором. Ответ 500 из-за `FOR UPDATE` недопустим.

## Область изменений

Не менялись основные макеты Figma, товарная логика, цена, авторизация, порядок миграций, база и Docker Volumes. Для чатов продавца используется прежняя внешняя навигация продавца, так как отдельные UI-экраны внутри приложения продавца не должны наследовать нижнюю навигацию покупателя.
