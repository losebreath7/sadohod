# R4 — миграции базы

Alembic подключён к запуску API. Первая ревизия — `20261115_01`.
В `backend/migrations/baseline_r3.py` зафиксированы 37 таблиц R3.
Ревизия не импортирует текущие модели приложения: последующие изменения
моделей не должны менять уже выпущенную миграцию.

## Как проходит обновление

1. Сценарий Windows собирает новый образ и останавливает прежний API.
2. Делает дамп, копирует его на компьютер и восстанавливает во временную
   базу `sadohod_verify_<случайный идентификатор>`.
3. На этой копии запускает миграции новым образом API. Сравнивает количество
   и контрольные суммы строк всех существовавших таблиц. В проверку попадают
   товары, павильоны, пути фото, переписки, бинарные вложения и векторы.
4. Повторяет миграцию на копии, чтобы проверить повторный запуск.
5. Удаляет только временную проверочную базу, сохраняет копии фото и настроек.
6. Если проверки успешны, запускает новый API. Он применяет те же миграции
   к рабочей базе до готовности `/health`.

При ошибке резервирования или репетиции новый API не запускается;
скрипт пытается вернуть прежний API, если тот работал. Автоматического отката
после запуска нового API нет. Архивы в `backups` нужно сохранять.
Репетиция запускается только для базы с проверочным именем, не для `sadohod`.

Эта первая миграция принимает совместимую прежнюю схему и добавляет недостающие
таблицы и индексы. Она проверяет колонки, типы, nullable, внешние ключи,
уникальность, первичные ключи и ожидаемые индексы. Несовместимая схема приводит
к остановке без отметки успешного перехода. Дополнительные сторонние таблицы
и индексы сохраняются. Проверка не заменяет аудит произвольных триггеров
и CHECK-ограничений, которые Alembic не сравнивает автоматически.

Для PostgreSQL сохранены расширение pgvector, размерности 96/512 и HNSW-индексы.
Миграции выполняются в транзакции с общей advisory-блокировкой. Для SQLite
используется `BEGIN IMMEDIATE`. Откат первой ревизии через `downgrade` запрещён,
чтобы случайно не удалить таблицы существующей установки.

## Следующие изменения схемы

Из каталога `server`, на отдельной базе разработки:

```sh
python -m alembic -c backend/alembic.ini current
python -m alembic -c backend/alembic.ini revision --autogenerate -m "describe change"
python -m alembic -c backend/alembic.ini upgrade head
python -m alembic -c backend/alembic.ini check
```

Адрес берётся из `DATABASE_URL`. Сгенерированную ревизию необходимо проверить
перед выпуском. Векторные таблицы исключены из автогенерации и изменяются
явным DDL. Не использовать `stamp head` для обхода ошибки несовместимой схемы.
Репетиция R4 требует неизменности всех существовавших строк; если следующая
миграция намеренно преобразует данные, её проверки нужно согласовать с этим
преобразованием. Добавленные файлы включать в `tools/release_files.txt`.

Использована схема передачи соединения из официального руководства Alembic:
https://alembic.sqlalchemy.org/en/latest/cookbook.html#sharing-a-connection-across-one-or-more-programmatic-migration-commands
